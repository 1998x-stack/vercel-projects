## 一、先侦察，不要凭名字猜功能

读这个仓库里真实存在的东西：`README.md`、`index.html`、全部 `.js`/`.css`、
数据文件（如 `data*.js`）、`docs/`、该仓库自己的 `AGENTS.md`/`CLAUDE.md`。
弄清楚：

1. 这是什么产品、给谁用、真实数据有哪些字段和取值范围；
2. 现有界面已经做了什么（功能区、交互、主题、搜索/筛选等）；
3. 现有界面的**具体缺陷**（死按钮、写死的统计、语法错误、注入风险、
   对比度不足、无响应式、CDN 依赖等）——逐条列出，实施时优先修。

数据缺失或无法核实时，写"待核验"，**不要编造**。README 声称的功能若无代码
支持，视为不存在。证据级别只用 `readme` / `vercel-metadata` / `source-inspection`
/ `name-only`，并在规范里标注。

## 二、先出设计规范，再实施

运行 ui-ux-pro-max 的检索拿到视觉方向（把真实命令与原始输出贴进规范）。然后写
`{{SPEC_PATH}}`，必须覆盖这八项，且每一项都要落到**这个项目**的真实内容上：

1. **信息架构** —— 页面分区、导航结构、层级与信息密度理由；
2. **视觉风格** —— 风格方向、来源（技能检索结果）、与产品气质的匹配理由；
3. **字体** —— 字体栈与理由（优先系统中文字体栈，避免外部字体请求）、
   字号阶梯、数字用等宽/tabular 的处理；
4. **配色** —— 语义令牌表（背景/表面/边框/正文/次要文字/强调/成功/警告/危险），
   每个令牌给出**浅色与深色两套值**，并给出实测对比度比值；
5. **组件** —— KPI 卡、图表、表格、筛选 chips、抽屉/侧栏、按钮、空状态、加载态、
   错误态，各自的形态与状态；
6. **交互** —— 筛选联动、搜索、主题切换、键盘可达性、`aria-live`、动效与
   `prefers-reduced-motion`；
7. **响应式布局** —— 明确断点与每个断点的布局变化（至少覆盖 375 / 768 / 1024 / 1440）；
8. **偏离记录** —— 凡是有理据地偏离技能建议的地方，写明偏离了什么、为什么
   （先例：正文用系统中文字体栈替代 Fira Sans）。

规范写完后再动手实现，不要边写边猜。

## 三、实施

- 沿用各仓库既有技术栈。仓库原本是零框架静态站点，就保持零框架。
- **零外部依赖**：不引入任何 CDN、外部字体、外部图标库或运行时网络请求；
  图表用手写内联 SVG 或 CSS，图标用内联 SVG。已存在的 CDN 引用要移除。
- 动态值一律用 `textContent` / `createElement` 写入，**不得**用 `innerHTML`
  拼接用户或数据内容。
- 可访问性目标准 WCAG 2.2 AA：正文对比度 ≥ 4.5:1，组件边界 ≥ 3:1，
  可见焦点，跳过主内容链接，触控目标移动端 ≥ 44px，语义化标签与 ARIA 正确。
- 深浅色双主题；主题偏好可持久化（如 `localStorage`），如先例那样支持
  URL 深链接更佳。
- 不改动数据层文件；不删除用户数据；保留历史快照目录（如 `v1/`、`v2/`）不动。
- 修掉第一步列出的既有缺陷，并在提交信息里逐条说明。

## 四、验证（必须是真实证据，不是声明）

按可用性依次尝试，并在提交信息中如实说明**做到哪一步、哪一步没做**：

1. 跑仓库自带的检查：`npm test`、`npm run check`、`npm run verify` 等（若存在且
   依赖已安装）。失败就必须修到通过。
2. 断点：375 / 768 / 1024 / 1440 下打开界面，确认无横向溢出、无布局塌陷。
3. 控制台：无 JS 报错，无 404，无外部网络请求。
4. 对比度：用脚本实算浅色与深色两套令牌的比值，把结果写进规范。
5. 交互：筛选/搜索/主题切换/键盘 Tab 各走一遍，确认可用。
6. 若本机可驱动 Chrome（CDP），导出截图到 `docs/screenshots/`
   （桌面浅色、桌面深色、移动端）。做不到就明确写"未做浏览器验证"，**不要伪造**。

## 五、提交

- 用 conventional commit，正文用中文，说明：设计依据、信息架构、修掉的既有缺陷、
  数据诚实性处理、可访问性结果、验证证据（命令与结果）与已知限制。
- **只 commit，不要 push**，编排脚本会在通过校验闸门后负责推送。
- 提交后 `git status` 必须干净——所有改动都要包含在提交里。
- 不要 `--force`，不要 rebase，不要改历史，不要动其他分支。

## 硬约束（违反即任务失败）

1. 只在当前工作目录内改动，绝不读写 `../` 下的其他项目仓库。
2. 不写入任何密钥、令牌、账号数据、私有源码到被跟踪的文件。
3. 不删除现有文件（除非它是本次改造中被替代且内容已并入新文件的重复产物，
   且必须在提交信息中说明）。
4. 不引入外部网络依赖；不写 `innerHTML` 赋值。
5. 不做未执行的验证就宣称通过；不编造数据、统计或功能。
6. 完成后输出一段简短总结：设计方向、改动的文件、验证结果、已知限制。
